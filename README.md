# Qadam Astana

Smart City MVP for choosing a single place or event in Astana within time,
location, and budget constraints. Backend foundation: S00/S01 (Sabyrzhan).
Frontend: React/Vite/TypeScript, owned by Damir; it is not generated by S00.
Backend: FastAPI/Pydantic. Target database: Supabase Postgres/PostGIS/pgvector.

## Windows PowerShell: run from the repository root

Python 3.12+ is required. These commands do not require activating a virtual
environment or changing the PowerShell execution policy.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
if (-not (Test-Path backend/.env)) { Copy-Item backend/.env.example backend/.env }
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

Copy the example only when `backend/.env` does not already exist; never overwrite
local credentials. In another PowerShell window, also at the repository root:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

Expected JSON: `{"status":"ok"}`. Health works without an `.env` file, API keys,
or a database. Interactive API documentation: <http://127.0.0.1:8000/docs>.
S01 adds real database coverage and unavailable search scaffolds. Health reports
process liveness; it does not prove database readiness.

## Configuration

Backend settings always read `backend/.env` relative to `settings.py`, regardless
of the current working directory. Runtime environment variables take precedence.
See `backend/.env.example`. Secrets stay on the server.

Damir's frontend uses `VITE_API_BASE_URL=/api` and optionally the public,
domain-restricted `VITE_TWOGIS_MAP_KEY`. The Vite development proxy should forward
`/api` to `http://127.0.0.1:8000`. Never expose `DATABASE_URL`, `OPENAI_API_KEY`,
or the server `TWOGIS_API_KEY` through a `VITE_` variable.

Real `.env` files are excluded from Git and Docker build context.

Python direct and transitive versions are pinned by `backend/requirements*.txt`
and `backend/constraints.txt`, including Windows `tzdata`. Constraints cover the
runtime and dev environments; pip installs only the requested dependency graph.
No new production dependency was added in S01. Python 3.12 is used in CI/Docker.

## Supabase database (server access only)

In Dashboard -> Connect, copy **Session pooler** (port 5432) into the local
`backend/.env` DATABASE_URL. Percent-encode reserved password characters. Do not
paste it into chat, Git or frontend settings. Append `?sslmode=require` when
there are no existing query parameters; use `&sslmode=require` otherwise.
The backend enforces TLS even when the URL omits sslmode; sslmode=disable/prefer
and Supabase direct/transaction-pooler URLs are rejected. With the Supabase CA,
prefer `sslmode=verify-full&sslrootcert=<local-path>`. The lazy pool defaults to
three connections (DATABASE_POOL_SIZE=1..5), with bounded checkout/connect/query
timeouts. Run one worker unless the total connection budget is adjusted.

Required Dashboard configuration: **Data API integration -> Enable Data API off**;
`app` must be absent from **API settings -> Exposed schemas**. The browser uses
only FastAPI `/api`; no Supabase browser client or database credential is needed.
The SQL migration also revokes schema/table access from PUBLIC/client roles and
enables RLS without client policies. Use the migration owner or an explicitly
configured trusted backend role; no anonymous write policies are created.
Dashboard state needs separate operator verification; SQL alone cannot prove
that the managed Data API switch is off. See actual status in the S01 handoff.

```powershell
.\.venv\Scripts\python.exe scripts/preflight.py --check db
.\.venv\Scripts\python.exe scripts/migrate.py
```

Migration 001 is atomic and tracked by SHA-256; replay verifies its checksum.
It creates `app.pois`, `poi_sources`, `poi_facts`, `embeddings`, `import_runs`
and a migration ledger. Existing extension schemas are discovered; new PostGIS,
vector and pg_trgm installations prefer `extensions`. No extension is dropped
or relocated. Follow-up migration 002 makes text/geo indexes conditional on
indexing rights and serializes embedding inserts with rights revocation.
Storage-only records are excluded from geo search. Geography uses SRID 4326;
embeddings use vector(1536), model,
dimensions and the hash of indexed source text. Import/embedding generation is
never run on startup. Do not edit an already applied migration.

Trusted ingestion must use `PostgresPOIRepository.upsert_pois`; its usage, stale
time/null rules and geo search are in [API v1.1](contracts/api-v1.md).
Partial imports never deactivate/delete absent POIs. No production corpus ships
with S01; `city_coverage=unknown` must not be presented as complete city coverage.

## API for D04

| Method | Path | Current behavior |
| --- | --- | --- |
| GET | `/api/health` | 200 `{"status":"ok"}`, no external calls |
| GET | `/api/coverage` | 200 real DB counters; 503 if unavailable/unmigrated |
| POST | `/api/recommendations` | S04 real-corpus alternatives; 200 ok/partial/unknown/no_match, unavailable 503 |
| POST | `/api/events/search` | S04 transient event v1.3: cards/listings/sources, unknowns preserved; unavailable 503 |
| POST | `/api/v2/events/search` | Explicit versioned alias for the transient event response |
| POST | `/api/v1/events/search` | Legacy persistent-event shape, unchanged 503 unavailable |
| POST | `/api/route` | Optional S02 walking: 200 known/unknown; disabled/unavailable 503, null total |

S00 `/api/v1/recommendations` remains an alias; `/api/v1/route` also works.
Event clients must select the new transient contract or the preserved legacy
path explicitly. Invalid input is sanitized JSON 422, internal failure
is generic JSON 500, and unknown `/api` paths are JSON 404. The SPA fallback
never captures `/api`. D01 must inspect non-2xx JSON instead of turning 503 into
an empty successful search. Request/response schemas and synthetic examples live
in `contracts/`. No event service implementation is modified by S01.

S04 connects Damir's unchanged D03 through the shared Responses `search_web`
client and Pydantic extraction. Runtime event sources explicitly prohibit
storage/indexing; HTTP uses `Cache-Control: no-store`. A separate listings array
retains discovered schedules that cannot become recommended sessions. Unknown
end, price-from, tickets or travel never become a confirmed fit. The bounded
web sample cannot establish `no_match` or complete city coverage.
Without a requested date, event discovery searches the next 30 days instead of
restricting results to today. A supplied date retains the selected local day
and earliest start; explicit time and budget limits still apply. Each event
keeps its source link and explicit session date/year/time. Source citation
titles may establish the event name, but never supply missing city, venue or
schedule facts. See [the event discovery fix](docs/handoffs/event-discovery.md)
for regression checks and live acceptance status.
See [the v1.3 event contract](contracts/api-v1.md#transient-event-discovery-s04-v13)
and [S04 checks and D04 handoff](docs/handoffs/S04.md). Existing POI and persistent
event schemas are unchanged. D04 frontend wiring is Damir's next consumer work;
this change does not edit his UI, normalizer, ingestion or data files.

S02's approved [route contract v1.2](contracts/api-v1.md#walking-route-s02-v12)
adds separate outbound/return_route metrics in meters/seconds, ephemeral
provenance and approximate destination warnings. Return travel is an independent
walking request; a failed leg leaves the total unknown. No geometry in S02.
2GIS remains disabled until server endpoint access AND project-specific runtime
rights are confirmed. See the separate capability gates in backend/.env.example;
TWOGIS_ENABLED alone is insufficient. Places is an internal live query only,
with no corpus, ranking or AI use. No new production dependency or DB migration.

```powershell
.\.venv\Scripts\python.exe scripts/twogis_smoke.py
```

This probes two public Astana landmark pairs (including opposite Esil banks)
and independent return legs, plus permitted discovery/Places, without printing
coordinates, keys or payloads. Exit 0 means all probes passed, 1 failure, 2 not_run.
Current access/rights blockers and D04 states: [S02 handoff](docs/handoffs/S02.md).

Unexpected HTTP exceptions are caught before the ASGI server can log their raw
messages. Only a generated request_id and a stable internal_error code are
logged; clients receive the same correlation ID in a generic JSON 500.

For local synthetic POI inspection only, set both `APP_ENV=development` and
`DEV_FIXTURE_MODE=true`, restart the backend, then GET `/api/dev/pois`.
Production rejects this endpoint even when the flag is set. Test POIs are
excluded from production coverage and default repository reads; never import
`contracts/examples` into the production corpus.

## One Docker image and first Render deploy

The root multi-stage Dockerfile builds Damir's frontend with Node, installs
Python dependencies, then serves API and SPA from a non-root Python process.
It requires D01's `frontend/package.json`, `package-lock.json` and working
`npm run build -> dist/index.html`. Without them the Node stage fails with
`D01 input missing`; no replacement frontend is generated.

D01 is published in origin/main through PR #1. A reviewed S01+D01 image was
built and tested in an isolated snapshot; the current S01 feature checkout does
not acquire frontend files automatically. Use a checkout containing both changes
for the full build. Damir's HTTP 503 unavailable-envelope fix is published in
origin/main (9141fc1, merge a9eb06c). Source inspection confirms the agreed
handling; a joint runtime check with that new frontend version remains not_run.

```powershell
docker build -t qadam-astana:s01 .
docker run --rm -p 8000:8000 --env-file backend/.env -e PORT=8000 qadam-astana:s01
```

Only the optional public `--build-arg VITE_TWOGIS_MAP_KEY=...` is supported.
`VITE_API_BASE_URL=/api` is fixed in the build. Never pass server secrets as
build arguments. Root `.dockerignore` excludes real env files at every depth;
the final stage copies only explicit application paths. The process binds
0.0.0.0 and reads the actual PORT. No migration/import/embedding startup hook.

After reviewed S01 and D01 code is available on the connected remote branch,
create a Render Blueprint from `render.yaml` (Docker, health `/api/health`).
Set DATABASE_URL in Render's runtime environment to the TLS Session pooler URL.
Automatic deploys are off. Add provider secrets later only when those features
are implemented; health/scaffolds do not need them. PORT is provided by Render.
Do not push merely to deploy without a separate PUSH instruction.

For an already prepared service, put RENDER_API_KEY and RENDER_SERVICE_ID in
the local process environment (never in files tracked by Git), then:

```powershell
$renderHeaders = @{ Authorization = "Bearer $env:RENDER_API_KEY" }
$renderDeploy = Invoke-RestMethod -Method Post -Uri "https://api.render.com/v1/services/$env:RENDER_SERVICE_ID/deploys" -Headers $renderHeaders -ContentType application/json -Body '{"clearCache":"do_not_clear"}'
Invoke-RestMethod -Uri "https://api.render.com/v1/services/$env:RENDER_SERVICE_ID/deploys/$($renderDeploy.id)" -Headers $renderHeaders | Select-Object id,status
# After status is live, use the actual service URL from Render:
Invoke-RestMethod "$env:API_BASE_URL/api/health"
Invoke-RestMethod "$env:API_BASE_URL/api/coverage"
curl.exe -i "$env:API_BASE_URL/api/not-real"
```

Verify frontend requests use the same HTTPS origin and `/api`. Record the actual
public API URL, response and deploy ID in the handoff. Missing D01/service access
is `not_run`, never a claimed deploy. [Render Docker](https://render.com/docs/docker),
[Blueprint fields](https://render.com/docs/blueprint-spec),
[trigger deploy API](https://api-docs.render.com/reference/create-deploy).

## Verification (repository root)

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m compileall -q backend/app scripts
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check backend scripts
.\.venv\Scripts\python.exe -m ruff format --check backend scripts
.\.venv\Scripts\python.exe scripts/export_contracts.py --check
.\.venv\Scripts\python.exe scripts/preflight.py --check all
```

Preflight checks are independent and read-only for the database. Responses and
embedding probes use synthetic text and may incur a small API charge. Missing
credentials or connectivity are recorded as `not_run`, not as a successful test.
The handoff records actual checks and any blockers.

Unit checks never use DATABASE_URL for integration tests. For real PostgreSQL
tests set TEST_DATABASE_URL to a **disposable test database** with TLS/DDL rights:

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests/test_repository_integration.py -q
```

Each test creates a random `test_s01_<12 hex>` schema and deletes only that schema
afterward. Missing TEST_DATABASE_URL explicitly skips these tests. Extensions
may be installed if absent and are never removed. CI provides an isolated TLS
PostgreSQL container, PostGIS and pgvector; no production secrets are required.
