## Implementation and data flow

- React 19/Vite 8/TypeScript, with package-lock.json and no Next.js, extra backend, auth or UI kit. [Frontend README](../../frontend/README.md) has dev/build/test/deploy commands.
- App renders a responsive single search screen: SearchForm, LanguageSwitch, ResultCard, EventCard and SourceDetails. POI recommendations and event/session searches are separate modes. Labels, source details, estimates, missing facts, route/fit/status/reason/activity codes and errors are visible.
- i18next/react-i18next/browser language detector use bundled src/locales/kk/common.json, ru/common.json and en/common.json. supportedLngs kk/ru/en, load languageOnly, fallback kk; qadam.language localStorage precedes navigator. resolvedLanguage controls requests and html.lang. Blocked storage is handled without breaking the screen.
- All requested inputs exist: query, manual point, minutes, return_to_start, KZT/person budget, indoor_only and Astana date/time. Defaults are not explicit. After edits, deliberate false, 0 and null stay in explicit_fields. Validation does not substitute city center, zero price, coordinates or dates for unknown data.
- Geolocation runs only on the button action, at most once per mounted screen. Denial/timeout/unavailable leave manual coordinates available. No watchPosition, query storage or GPS history. Late GPS results do not overwrite a newer manual/map choice. The current point source is shown.
- Optional public MapGL loads only when VITE_TWOGIS_MAP_KEY is supplied. Map center is only a viewport, not a selected origin. Click order longitude/latitude is converted to contract latitude/longitude; markers/map are cleaned up. Manual entry works without a map/key.
- format.ts uses Intl kk-KZ/ru-KZ/en-GB, KZT and Asia/Almaty. datetime-local is interpreted as Astana wall time independently of the browser timezone, then sent as an aware ISO instant. Native datepicker controls may use the browser/OS UI language.
- Types mirror v1 schemas; api.ts validates request/response structure and cross-field rules, locale/source/correlation invariants, and uses only relative /api with timeout/abort. It does not expose raw provider/server errors or log queries/coordinates.
- App starts with real health and live API mode. Loading, error/retry, unknown, unavailable and no_match/empty remain separate. New search, language/mode change, live reset and unmount invalidate older responses, including delayed dev fixtures.
- An explicit expandable dev preview loads original contract fixtures. English generated fixture text and source names remain unchanged and visibly synthetic. No automatic fallback after API failure. Production excludes dev controls and fixture payloads.

Flow: UI + resolved language -> validated snake_case SearchRequest -> same-origin /api -> backend -> validated v1 response -> localized code labels plus unchanged source facts/generated text with its declared language. Defaults/null/false/zero are preserved; no shared contract changes were needed.

## Concepts for handoff

- Why resolvedLanguage? It is the supported language actually backed by bundled resources, unlike a detected regional/unsupported value.
- Why explicit_fields? A deliberate false, zero or null must not be overwritten by later text inference; untouched defaults may still be inferred.
- Why is 404/unavailable not no_match? A missing search/provider cannot establish that an available corpus contains no eligible destination.

Study the form -> contract -> API -> rendering flow, AbortController/generation ownership, same-origin deployment routing, source provenance vs generated explanation and the difference between mock tests, live health and live search readiness.
