## Data flow and interfaces for Damir

Health: HTTP GET -> FastAPI -> HealthResponse -> `{"status":"ok"}`. There are no
external calls on this path.

Later search: frontend -> `/api/v1/recommendations` or `/api/v1/events/search` ->
Pydantic request -> normalization/retrieval/constraint checks -> sourced cards ->
the shared response envelope. These search paths are reserved and return 404 in
S00; D01 should use contract fixtures while backend stages are implemented.

The request uses request_id, query, locale kk/ru/en, nullable origin and
available_minutes, return_to_start, nullable budget_kzt_per_person, indoor_only,
aware date_time and explicit_fields. Explicit structured values win over inferred
text, including false, zero and null. Null budget is not a free-only budget.

Every response has status, items (at most three), warnings, sources, request_id.
Cards include provenance, reason_codes, activity_code, visit_minutes_estimate,
route_status, travel_minutes_estimate, fit_status, missing_fields, explanation,
generated_locale and action. Unknown/unavailable/no_match are separate states.
Observation time can be null; zero travel is valid only for a known/estimated
route, not a substitute for an unknown route. Event and session are separate.

Import `POIRepository` from `backend.app.repository`:

```python
async def upsert_pois(records: Sequence[Mapping[str, object]]) -> UpsertResult:
    ...
```

Upsert identity is (primary source provider, external_id); preserve stored IDs.
Return inserted/updated/rejected counts and zero-based rejection indexes/codes.
Within a batch, first valid identity wins; later duplicates are rejected.
Infrastructure failure rolls back accepted writes and raises, not fake counts.
The full contract defines permissions, stale data, sources and null handling.
No direct ingestion SQL or separate client implementation should bypass it.

## Important concepts and interview preparation

Study contract-first development, Pydantic vs JSON Schema cross-field checks,
environment precedence, lazy provider initialization, async resource cleanup,
source provenance/rights, unknown vs unavailable vs no_match, and the difference
between a mocked vector test and a real embedding/API check.

1. Why does health not prove database readiness? It reports process liveness
   without touching integrations; the separate DB preflight records readiness.
2. Why are event and session separate? One event can have several occurrences
   with distinct starts, ends, prices and cancellations; unknown times stay unknown.
3. Why use both JSON Schema and Pydantic tests? The former is portable to the
   frontend/ingestion; the latter also verifies rights, source references,
   session relationships and honest response-state invariants.
